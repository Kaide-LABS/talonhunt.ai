 Architectural Transformation Report: TalonHunt Anti-Cheat Code Editor Migration to Serverless Infrastructure1. Executive Analysis of the Architectural Paradigm ShiftThe proposed migration of the TalonHunt Anti-Cheat Code Editor to a technical stack predicated on MongoDB for persistence and Netlify for deployment represents a foundational shift in architectural philosophy, moving from a stateful, connection-oriented model to a stateless, event-driven serverless paradigm. This transition is not merely a substitution of hosting providers but a fundamental re-engineering of how the application handles concurrency, real-time data integrity, and the adversarial relationship with sophisticated cheating tools like Cluely and Interview Coder.In the traditional monolithic architecture typically employed for Online Integrated Development Environments (IDEs), a persistent server process (often Node.js or Python) maintains a continuous WebSocket connection with the client. This allows the server to hold the session state in memory, instantly validate keystrokes, and execute code within a local child process. The server acts as the single source of truth and the immediate arbiter of integrity. By adopting Netlify, TalonHunt moves to an ephemeral compute model based on the Jamstack philosophy. There is no permanent "server" overseeing the exam session. Instead, the backend relies on discrete, stateless functions—powered by AWS Lambda and Deno-based Edge Functions—that spin up on demand to handle specific requests and terminate milliseconds later.This architectural inversion offers immense benefits in terms of infinite horizontal scalability and operational simplicity. When ten thousand students begin a concurrent exam, Netlify’s edge network and serverless infrastructure automatically scale to meet demand without the manual provisioning of load balancers or potential for server crashes that plague monolithic VPS setups. However, this shift imposes strict constraints that require rigorous engineering solutions. The stateless nature of Netlify Functions means standard WebSockets are impossible to maintain directly, necessitating a reliance on third-party real-time infrastructure. Furthermore, the ephemeral nature of the backend complicates database connection management, as the traditional method of maintaining a persistent connection pool to MongoDB is fundamentally incompatible with a model where thousands of isolated functions may launch simultaneously.The threat landscape also shifts. Tools like Cluely operate as undetectable AI assistants that read screen content and inject answers via overlay windows, often exploiting the latency between client action and server verification.1 In a serverless environment, where complex anomaly detection algorithms cannot run continuously on a live stream without incurring prohibitive costs, the detection logic must be decoupled into asynchronous pipelines. The immediate validation must move to the client-side edge, hardened by cryptographic signatures, while heavy-duty behavioral analysis is deferred to scheduled background processes. This report details the exhaustive technical modifications, risk mitigations, and architectural patterns required to deliver a robust, secure, and responsive TalonHunt environment under these specific constraints.2. The Persistence Layer: MongoDB Strategy in a Serverless EnvironmentThe decision to utilize MongoDB as the primary data store provides significant advantages for TalonHunt, particularly regarding the flexible schema requirements of storing diverse code submissions, telemetry logs, and detection heuristics. However, the interaction between Netlify’s serverless functions and MongoDB’s connection-oriented protocol requires a specialized architectural approach to avoid latency spikes, connection exhaustion, and "thundering herd" scenarios.2.1. Managing the "Thundering Herd": Connection Pooling and CachingIn a traditional long-running server application, the backend initializes a MongoClient instance once upon startup. This client establishes a pool of TCP connections (typically 5 to 100) to the MongoDB cluster, which are reused for all subsequent incoming requests. The handshake overhead—DNS resolution, TCP connection establishment, TLS negotiation, and SASL authentication—is incurred only once.In the Netlify serverless model, every HTTP request to the API triggers the invocation of a function that runs in an isolated container. If the application naively initializes a new MongoDB connection inside the function handler for every request, the consequences are catastrophic for an exam platform.First, the latency penalty is severe. The connection handshake process can take between 200ms and 500ms, depending on network distance and SSL complexity.3 If this latency is added to every keystroke save or code compilation request, the editor will feel sluggish, directly impacting the user experience and potentially causing students to lose flow during high-stakes assessments.Second, and more critically, is the risk of connection exhaustion. If 500 students begin an exam simultaneously, Netlify will spin up 500 concurrent Lambda instances. If each instance attempts to open a new connection pool (even with a default size of 5), the MongoDB cluster will suddenly receive 2,500 connection requests. This will instantly hit the maxIncomingConnections limit configured on standard MongoDB Atlas clusters, causing the database to reject new connections. The application would crash precisely when reliability is most critical.To mitigate this, TalonHunt must implement a Global Scope Caching pattern. In the Node.js runtime environment used by Netlify Functions, the global context of the module is preserved between invocations if the underlying container is reused (a "warm start"). The engineering team must structure the database connection logic to check for an existing cached client before attempting to connect.The implementation requires defining a variable for the cached client outside the exported handler function. When a request arrives, the code first checks if this variable is populated and if the connection is still active. If so, it reuses the existing client, bypassing the handshake entirely and reducing database latency to near-zero. If the variable is null (a "cold start"), it establishes a new connection and stores it in the global variable for future use. Furthermore, the configuration of the MongoClient must be strictly tuned for serverless environments. The maxPoolSize parameter must be set to 1. Since a serverless function processes only one event at a time, maintaining a pool of multiple connections per function is wasteful and dangerous. This ensures that even at maximum concurrency, the number of open connections to the database maps 1:1 with the number of active execution environments, preventing the cluster from being overwhelmed.2.2. Schema Design for High-Frequency Telemetry and BiometricsTalonHunt’s anti-cheat mechanism relies heavily on analyzing behavioral biometrics—typing rhythm, backspace usage, copy-paste frequency, and focus switching—to detect AI generation or external assistance.4 This detection strategy generates a massive volume of write operations. A typical coding session involves thousands of keystrokes, each carrying metadata about timing, latency, and key codes.If the application were to send a write request to MongoDB for every single keystroke, the throughput costs on MongoDB Atlas would skyrocket, and the operational latency would degrade the exam experience. Moreover, standard MongoDB documents are not optimized for this type of high-velocity, append-only sensor data. A naive approach of pushing event objects into a single array within a Session document would quickly encounter MongoDB’s 16MB document size limit, leading to write failures for longer exams.The technical plan must therefore incorporate MongoDB’s native Time Series Collections, introduced in MongoDB 5.0. This feature is specifically designed to handle high-frequency data streams efficiently. The schema should be defined with a timeField representing the event timestamp and a metaField containing the session_id and student_id. The granularity setting should be configured to 'seconds' to optimize the internal storage format for the bursty nature of typing. This internal optimization allows MongoDB to group time-adjacent data points into compressed buckets on disk, significantly reducing storage costs and improving read performance for analytical queries.However, even with Time Series collections, the network overhead of an HTTP request per keystroke is unsustainable from a Netlify function invocation perspective. The client-side architecture must implement a Buffered Write Strategy. The frontend code editor should maintain a local circular buffer of telemetry events. This buffer accumulates keystroke and cursor data until a specific threshold is reached—either a time interval (e.g., every 5 seconds) or a size limit (e.g., 50 events). Once the threshold is met, the client flushes the buffer to the Netlify backend in a single batched HTTP POST request. This reduces the number of database write operations and serverless function invocations by a factor of 50 or more, aligning the architecture with the cost and performance realities of the cloud.2.3. Data Aging and Archival PoliciesThe value of anti-cheat telemetry is highly time-sensitive. The granular keystroke data is critical during the exam for live proctoring and immediately after for forensic analysis of suspicious sessions. However, once an exam is graded and the review period has passed, the utility of second-by-second biometric data diminishes rapidly, yet it occupies significant storage space. Maintaining terabytes of historical keystroke logs on a high-performance NVMe-backed MongoDB cluster is financially inefficient.The migration plan must include the configuration of MongoDB Atlas Online Archive. This feature allows TalonHunt to define automated data aging policies based on the timestamp of the telemetry data. A recommended policy would be to automatically move data older than 90 days from the hot cluster to cold, S3-backed object storage. This process is transparent to the application; queries that require historical data can still access the archived logs (albeit with higher latency), but the active cluster remains lean and responsive. This tiered storage architecture ensures that the system remains cost-effective as it scales to handle years of exam data across thousands of students.3. Compute Architecture: Netlify Functions and Edge LogicThe adoption of Netlify dictates a split-compute architecture. TalonHunt will rely on standard Netlify Functions (running Node.js on AWS Lambda) for heavy business logic and database interactions, and Netlify Edge Functions (running Deno on the network edge) for latency-sensitive operations like authentication routing and initial session validation.3.1. Mitigating Cold Starts for Real-Time ResponsivenessOne of the most persistent challenges in serverless architectures is the "Cold Start" phenomenon. When a serverless function has not been invoked for a certain period (typically 5 to 15 minutes), the cloud provider reclaims the compute resources. The next request requires the provider to provision a new container, download the function code, start the runtime environment, and execute the initialization logic. For a Node.js function, this process can introduce a latency of 1 to 3 seconds, or even longer for complex applications.5For an anti-cheat system, this latency is problematic. If a student attempts to load a question or submit an answer and encounters a 3-second delay, it creates anxiety and disrupts the cognitive flow of the assessment. It may also lead to false positives in the anti-cheat system if the latency causes a discrepancy between the client-side timestamp and the server-side receipt timestamp.To mitigate this, the technical plan must prioritize Code Bundle Optimization. The backend code deployed to Netlify must be aggressively tree-shaken. Developers must avoid importing massive monolithic libraries. For example, instead of importing the entire aws-sdk to upload a file to S3, the application should import only the @aws-sdk/client-s3 module. This reduces the size of the function zip file, speeding up the download and decompression phase of the cold start.Furthermore, critical paths that require immediate responsiveness—such as the initial "Start Exam" check or the authentication handshake—should be moved to Netlify Edge Functions. Unlike standard functions, Edge Functions run on the V8 isolate engine directly at the CDN edge nodes close to the user. They have near-zero cold start times because they do not require booting a full container or OS. By handling the initial request validation at the edge, TalonHunt can provide instant feedback to the user ("Exam Loading...") while the heavier standard functions warm up in the background.73.2. The Execution Timeout Constraint and Code SandboxingNetlify Functions have a strict execution time limit, defaulting to 10 seconds (configurable up to 26 seconds on higher plans). This imposes a hard constraint on the "Code Runner" feature of the IDE. If a student writes an infinite loop or a computationally intensive algorithm, a synchronous execution request handled by a Netlify Function would simply time out, potentially leaving the frontend in an undefined state. Furthermore, executing untrusted user code inside the same environment that holds database credentials poses a catastrophic security risk (Remote Code Execution).Therefore, the architecture for the code execution engine must be decoupled from the Netlify backend. TalonHunt cannot run the student's code on Netlify. The technical plan must incorporate an external Sandbox Execution Environment. There are two viable approaches for this integration.The first is to utilize a third-party compilation API such as Judge0 or Piston. In this model, the Netlify Function acts as a proxy, forwarding the student's code to the external API and returning the result. This offloads the compute risk and security isolation to a specialized provider.The second, and potentially superior approach for an anti-cheat context, is to leverage WebAssembly (Wasm) to execute code directly in the client’s browser. Languages like Python (via Pyodide) can run entirely within the browser sandbox. This eliminates network latency for code execution, providing a "local" feel to the IDE. However, for the final submission, a server-side validation is still required to prevent tampering. A hybrid approach is recommended: use Wasm for the rapid "run/debug" cycle during the exam, and use an asynchronous call to a secure external sandbox for the final "grade/submit" action, ensuring that the results are authoritative.3.3. Skew Protection and Deployment ConsistencyTalonHunt is a critical assessment platform where session continuity is paramount. A significant risk in continuous deployment environments like Netlify is "Version Skew." If the development team pushes a bug fix or feature update while an exam is in progress, the deployment ID of the application changes. A student who loaded the exam interface 30 minutes ago is running version v1.0 of the JavaScript client. If they attempt to call a serverless function endpoint that has been updated to v1.1 (perhaps expecting a different payload structure), the request may fail, causing data loss or a disruption of the exam.Netlify’s Skew Protection feature is designed to address this by pinning asset and function versions to the specific deployment that the user initially loaded.8 When Skew Protection is enabled (via NETLIFY_NEXT_SKEW_PROTECTION=true for Next.js applications), Netlify uses a cookie or header to route the user's requests to the immutable version of the functions that match their client assets. For TalonHunt, enabling this feature is non-negotiable. It ensures that even if a new version of the platform is deployed mid-exam, active sessions continue to operate on the consistent set of logic they started with, preventing mysterious API failures that could be misconstrued as technical issues or cheating attempts.4. The Real-Time Conundrum: WebSockets and Pub/Sub MiddlewareThe migration to Netlify introduces a profound challenge regarding real-time capabilities. The original TalonHunt plan likely envisioned a stateful server managing persistent WebSocket connections to stream student activity to a proctor dashboard. However, Netlify Functions are stateless and ephemeral; they cannot maintain open TCP connections for WebSockets.9 They are designed to receive a request, process it, and die. This architectural limitation necessitates the integration of a dedicated real-time middleware layer.4.1. Selecting a Middleware: Ably vs. PusherTo restore real-time functionality—vital for live proctoring, instant warnings, and chat—TalonHunt must utilize a hosted Pub/Sub provider. The research highlights Ably and Pusher as the primary candidates.10 A deep technical comparison reveals that Ably is the superior choice for the specific requirements of an anti-cheat platform.The critical differentiator is Connection State Recovery and Message Ordering.11 In a remote exam setting, students often have unstable internet connections. If a student's Wi-Fi drops for 10 seconds, they might reconnect with a new socket ID. Pusher, particularly on lower tiers, may treat this as a new session, potentially dropping the messages (code edits) that occurred during the disconnect. Ably, by contrast, is architected to guarantee message delivery and ordering upon reconnection. It effectively "replays" the missed events. For an anti-cheat system, this is vital. If the system is reconstructing a timeline of code edits to prove or disprove authorship, the sequence of operations must be mathematically precise. Missing a "paste" event or receiving a "delete" event before the corresponding "type" event would corrupt the forensic audit trail.4.2. Implementing the Ably-Netlify PatternThe integration follows a specific pattern to bridge the stateless and stateful worlds. The client (student browser) connects directly to Ably using an auth token generated by a Netlify Function. When the student types or compiles code, the client publishes an event to a private Ably channel (e.g., exam:session_123). The proctor’s dashboard subscribes to this channel, receiving the update in milliseconds via Ably's infrastructure, completely bypassing the Netlify backend.However, this data must eventually be persisted to MongoDB. Relying on the client to send data to both Ably (for proctors) and Netlify (for storage) is redundant and unreliable (dual-write problem). Instead, TalonHunt should utilize Ably Integrations (Webhooks). Ably can be configured to buffer messages and send a batched HTTP POST request to a specific Netlify Function endpoint (/api/webhooks/persist-session) whenever a certain number of messages accumulate or the session ends. This decouples the real-time stream from the storage layer. The live interaction remains lightning-fast, limited only by Ably’s edge latency, while the database persistence happens asynchronously, optimizing the write throughput to MongoDB and insulating the database from the "firehose" of real-time packets.4.3. Collaborative Editing with JamsocketIf the TalonHunt roadmap includes a "Pair Programming Interview" mode where an interviewer and candidate edit code simultaneously, the Pub/Sub model of Ably is insufficient. Collaborative editing requires Conflict-Free Replicated Data Types (CRDTs) or Operational Transformation (OT) to handle simultaneous edits without race conditions. These algorithms generally require a central authority or a stateful peer to merge changes.Since Netlify Functions cannot hold this state, TalonHunt must leverage the Jamsocket Extension for Netlify.12 Jamsocket allows the deployment of stateful WebSocket backends (essentially "Session Backends") that spin up as micro-VMs or lightweight containers. When an interview starts, a Netlify Function calls the Jamsocket API to spawn a dedicated backend process for that specific room. This backend runs a Yjs or Automerge server, maintaining the document state in memory for the duration of the session. The client connects to this Jamsocket instance for the editing experience. This hybrid approach allows TalonHunt to remain primarily serverless while spinning up "ephemeral servers" only when the specific use case of collaborative editing demands it.5. Anti-Cheat Telemetry and Detection PipelinesThe core value proposition of TalonHunt is the integrity of the assessment. The migration to a distributed, stateless architecture fundamentally changes the threat vectors and the mechanisms available for detection, particularly against advanced tools like Cluely.5.1. Countering "Cluely" and Screen-Reading AICluely represents a new class of cheating tools that operate entirely outside the browser context.1 It functions as a desktop application that captures the screen buffer and system audio, sends it to an LLM, and displays the answer in a transparent overlay window that sits "on top" of the browser. Because Cluely does not inject code into the DOM or modify the network traffic of the exam page, traditional browser-based detection methods (inspecting the DOM for foreign elements) are ineffective.In a server-based architecture, one might attempt to stream a video of the screen to the server for computer vision analysis, but the bandwidth and processing costs of this are prohibitive in a serverless model. Instead, TalonHunt must rely on Behavioral Heuristics and Client-Side Edge Detection.The "Cluely" user exhibits a specific behavioral signature: they read the question, wait (latency while the AI processes), and then transcribe the solution. This transcription often happens at a superhuman speed or with a distinct lack of non-linear editing (no jumping back to fix typos, just a linear stream of perfect code). TalonHunt must implement a Keystroke Dynamics Engine in the browser using WebAssembly. This engine calculates metrics such as "Flight Time" (time between key up and next key down) and "Digraph Latency" (speed of specific key pairs). If the variance in typing speed is near zero (robotic) or if the speed exceeds human physiological limits, a flag is raised.Furthermore, Cluely users often rely on an overlay window. While the browser cannot "see" the overlay, it can detect Focus Loss. If the student clicks on the Cluely window to scroll the AI's answer, the window.blur event fires in the browser. However, sophisticated cheaters know this and use "always on top" windows that don't steal focus. To counter this, TalonHunt can employ Page Visibility API and potentially Mouse Tracking. If the mouse cursor tracks lines of text that are not being highlighted or interacted with (mimicking the user reading the overlay), this anomaly contributes to the risk score.5.2. Distributed Detection LogicIn the serverless model, we cannot run a heavy Python ML model on every request to check for cheating. The architecture requires a split-brain approach:Synchronous (Edge) Logic: Lightweight rules are evaluated in the browser and confirmed by the Edge Function on ingestion. Examples include checking for "Paste" events that exceed 500 characters or detecting if the user attempts to open the developer console. These result in immediate warnings via Ably.Asynchronous (Scheduled) Logic: The raw telemetry data stored in MongoDB is analyzed post-hoc. TalonHunt can utilize Netlify Scheduled Functions (Cron) to wake up every 10 or 15 minutes. This function queries the recent telemetry from MongoDB for active sessions and feeds it into a more sophisticated anomaly detection algorithm. This algorithm can look for global patterns, such as comparing the student's current code complexity against the time elapsed. If a student writes a complex dynamic programming solution in 3 minutes with linear typing, the asynchronous worker flags the session for human review. This delay (minutes rather than seconds) is an acceptable trade-off for the cost efficiency of serverless execution.5.3. Integrity of the Telemetry StreamA major risk in client-side detection is that the student, who controls the browser, can tamper with the detection code. They could disable the JavaScript that reports the "Paste" event. To combat this, TalonHunt must implement a Heartbeat Integrity Protocol.The client is expected to send a telemetry heartbeat every 10 seconds, signed with a session-specific JWT. If the Netlify backend (or the Ably webhook handler) stops receiving this heartbeat, but the WebSocket connection remains active (meaning the student is online), it indicates that the monitoring script has been suppressed. The system can then trigger an automatic "Connection Error" on the client, pausing the exam and forcing a reload (which re-initializes the tamper-proof scripts). Additionally, the telemetry payload should include a hash of the client-side code bundle. If the student modifies the local JS file to bypass a check, the hash sent in the heartbeat will mismatch the expected hash on the server, triggering an immediate violation.6. Observability and Operational ResilienceMigrating from a monolith to a distributed system composed of Edge Functions, Serverless Functions, MongoDB, and Ably dramatically increases the complexity of debugging. When a student claims "the system didn't save my answer," identifying whether the failure occurred in the browser, the Pub/Sub layer, the Netlify function, or the database write requires advanced observability.6.1. Implementing OpenTelemetryThe technical plan must include the integration of OpenTelemetry (OTel).15 OTel provides a vendor-neutral standard for generating traces and metrics. TalonHunt should instrument its Netlify Functions using the Node.js OTel SDK (or @vercel/otel wrapper).The tracing strategy must cover the entire request lifecycle. When the client initiates a "Save," it generates a traceparent ID. This ID is passed in the HTTP headers to the Netlify Function. The Function includes this ID in its logs and passes it as metadata in the MongoDB operation comments. This creates a "Distributed Trace" that allows engineers to visualize the request as a waterfall graph. They can see exactly how long the MongoDB connection took, how long the Ably publish took, and if the function timed out.6.2. Logging Strategy and Cost ControlIn a high-frequency system, logging every event can be prohibitively expensive. OpenTelemetry allows for Sampling, where only a percentage of successful requests (e.g., 5%) are fully traced, while 100% of error requests are captured.17 This ensures that if a student encounters a bug, the data is available, but the system is not overwhelmed with logs of successful "heartbeat" signals. The logs should be structured as JSON 18 to allow for programmatic querying (e.g., "Show me all errors for Session ID 123").7. Security and ComplianceThe transition to Netlify and MongoDB Atlas necessitates a review of data security, particularly given the sensitive nature of academic records and student identity.7.1. Stateless Authentication and Identity ManagementNetlify Functions are stateless, meaning they cannot rely on server-side sessions stored in memory. Authentication must be handled via JSON Web Tokens (JWTs). The recommended approach is to use Netlify Identity (powered by GoTrue) or an external provider like Auth0 or NextAuth.When a student logs in, they receive a JWT. This token is sent in the Authorization header of every request. The Netlify Edge Functions can verify the signature of this token at the edge, rejecting unauthorized requests before they consume expensive backend resources. To prevent Cross-Site Scripting (XSS) attacks from stealing the token, it should be stored in an HttpOnly, Secure, SameSite cookie, rather than in LocalStorage.7.2. Content Security Policy (CSP)To prevent code injection attacks and to hinder the effectiveness of some browser-based cheating overlays, TalonHunt must implement a strict Content Security Policy. Netlify allows defining these headers in the netlify.toml configuration file.The CSP should restrict script-src to the application's own origin and the Ably CDN. Crucially, it should set frame-ancestors 'none'.1 This directive prevents the TalonHunt exam environment from being loaded inside an <iframe> on a malicious site. Some cheating services try to wrap the exam in a framed window to intercept events or overlay control layers; this header physically blocks the browser from rendering the page in that context.7.3. Data Residency and GDPRIf TalonHunt serves international students, data residency becomes a compliance issue. MongoDB Atlas allows the selection of specific cloud regions for data storage. To minimize latency, the MongoDB cluster should be deployed in the same AWS region as the primary Netlify functions (typically us-east-1 by default, but configurable on Enterprise plans). For GDPR compliance, relying on a single global region may not be sufficient. The architecture may need to support Sharding in MongoDB, where data is physically partitioned based on the student's region field, directing European students' data to a shard located in Frankfurt or Dublin, while US students' data remains in Virginia. Netlify’s Edge Functions are geo-aware and can route traffic to the appropriate regional API endpoints to respect these boundaries.8. Final RecommendationThe engineering team must prioritize the Connection Caching mechanism and the Ably Integration as the first critical milestones. Failure to handle the database connections correctly will lead to immediate instability under load, while the lack of a robust Pub/Sub layer will render the live proctoring features non-functional. The result is a system that is "born global," resilient by design, and prepared for the future of distributed, secure assessment.
