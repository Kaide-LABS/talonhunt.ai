 Behavioral Forensics in Engineering: Distinguishing Cognitive Reference from Generative Transcription via Keystroke Dynamics1. Introduction: The Hypocrisy of Focus in the Age of Generative AIThe integration of Large Language Models (LLMs) into the software development ecosystem has precipitated a crisis of verification in both academic and professional environments. The central tension, as articulated in the foundational query for this report, lies in the "hypocrisy of focus loss." In traditional pedagogy and proctoring, the act of "switching tabs"—diverting focus from the primary Integrated Development Environment (IDE) to an external application—has historically been viewed with suspicion, a binary proxy for disengagement or dishonesty. Yet, this view fundamentally conflicts with the reality of modern engineering, which is an intrinsically multimodal activity requiring the continuous synthesis of external documentation, API references, and legacy codebases.1To penalize a developer for leaving the IDE is to penalize the very research behaviors that constitute competent engineering. A developer who does not consult documentation is often operating on stale memory or guessing at syntax, behaviors that lead to inefficient and error-prone code. Therefore, the "focus loss" event is not, in itself, an indicator of academic or professional dishonesty. It is a neutral event—a "probe" into the user's external cognitive environment. The dishonesty—or the "Bad Focus Loss"—resides not in the departure from the IDE, but in the nature of the return.The core thesis of this report is that the behavioral signature of a user returning from a cognitive task (reading documentation) is biometrically distinct from a user returning from a transcription task (copying AI-generated text). This distinction is observable through Keystroke Dynamics, a behavioral biometric that analyzes how a person types rather than what they type.3 By leveraging insights from cognitive load theory, specifically the "switch costs" associated with multitasking 4 and the working memory limits defined by Miller's Law 5, we can construct a "Cluely" logic that distinguishes these states with high fidelity.This report provides an exhaustive analysis of the physiological and cognitive mechanisms that underpin these two distinct behaviors. We will explore how authentic composition, even when supported by documentation, retains a "bursty," non-linear, and hesitant character driven by the high cognitive load of synthesizing information.6 In contrast, we will demonstrate that "Bad Focus Loss"—specifically the manual transcription of LLM output to bypass copy-paste detection—exhibits a high-linearity, rhythmic oscillation driven by the constraints of short-term memory buffering.7 By shifting the detection paradigm from "Prevention of Access" to "Verification of Authorship Process," we can resolve the hypocrisy of focus loss, allowing engineers to use the open web for legitimate research while robustly identifying those who substitute generative retrieval for cognitive effort.2. The Cognitive Architectures of Coding and TranscriptionTo differentiate "Good Focus Loss" (Documentation) from "Bad Focus Loss" (ChatGPT), we must first deconstruct the neurological processes occurring during the "Time Away" ($T_{away}$) and the "Recovery Phase" ($T_{recovery}$). The user's subjective experience—that they are "checking docs"—corresponds to a specific cognitive state known as Information Foraging, which imposes a heavy tax on working memory and executive function. Conversely, using ChatGPT corresponds to a state of Generative Retrieval, which fundamentally alters the cognitive load from semantic processing to orthographic buffering.2.1 The Cognitive Cost of Context Switching (The "Switch Cost")Research in cognitive psychology has long established that true multitasking is a myth; the human brain functions serially, engaging in rapid task switching that incurs a measurable "switch cost".4 This cost is not merely time lost; it is a temporary degradation in cognitive efficiency as the brain reconfigures its "task set"—the configuration of mental resources, goals, and active memory buffers required to perform a specific action.When a developer switches tabs to read documentation (Good Focus Loss), they are initiating a Complex Task Switch. They move from a "Production Mode" (writing code) to a "Comprehension Mode" (reading technical text). This switch involves several high-order cognitive operations:Disengagement: The user must suspend the current mental model of the code they are writing, holding the cursor position and the immediate logic goal (e.g., "I need to sort this array") in a suspended state.Search and Filter: Upon entering the documentation (e.g., Unity Burst Compiler docs 1), the user must scan headers, filter out irrelevant API versions, and locate the specific syntax required. This is a high-attention task.Synthesis: The user does not simply memorize the text. They must translate the generic example (e.g., void Example(int x)) into their specific context (e.g., void PlayerController(int health)). This requires semantic mapping.Re-engagement: When switching back to the IDE, the user faces a "Refractory Period." They must reload the suspended context of their own code and integrate the newly acquired, synthesized information.Implication for Keystroke Dynamics: This heavy cognitive load creates a High Return-to-Editor Latency (REL). Upon returning to the tab, the user rarely types immediately. There is a "cognitive pause" or "settling time" of several seconds where the brain aligns the new information with the old context.9 Furthermore, the initial typing is often tentative, characterized by pauses before the retrieved syntax is typed, as the user verifies the mapping from the generic example to their specific variable names.6Contrast this with the "Switch Cost" of using an LLM for transcription (Bad Focus Loss). In this scenario, the user prompts the LLM (e.g., "Write a Unity Burst Job for sorting"). The LLM produces a complete, context-perfect block of code. The user's task is now Simple Task Switching:Visual Acquisition: The user looks at the generated code.Buffering: The user memorizes a sequence of characters (e.g.,  public struct).Motor Transfer: The user switches back to the IDE.Dump: The user types the buffered characters immediately.Implication for Keystroke Dynamics: The cognitive load here is low because the synthesis step is skipped. The LLM has already done the semantic mapping. The user is merely acting as a data conduit. Consequently, the Return-to-Editor Latency (REL) is extremely low. The user often begins typing within milliseconds of the window focus event because the information is held in the volatile "phonological loop" of working memory, which decays rapidly.10 The urgency to "dump" the buffer before it fades drives a rapid, immediate onset of typing.2.2 Working Memory Limits: The Miller’s Law ConstraintA critical discriminator for "Bad Focus Loss"—specifically when the user is manually typing the AI output to avoid paste detection—is the limitation of human short-term memory. In 1956, cognitive psychologist George Miller proposed that the average human working memory capacity is limited to $7 \pm 2$ "chunks" of information.5 A "chunk" can be a single digit, a word, or a familiar syntax unit (like for ().When a user reads documentation (Good Focus Loss), they are not constrained by Miller's Law in the same way because they are retrieving concepts, not strings. A user can read a complex paragraph about "Burst Compiler Float Precision" 1, understand the concept of FloatMode.Fast, and return to the editor to implement it. They might type for minutes based on that single concept lookup because they are generating the implementation, not recalling the text verbatim.However, when a user is transcribing code from an LLM (Bad Focus Loss), they are typically engaging in "verbatim transcription." Unless they are extremely proficient typists who can "touch type" while looking at a second screen, they must rely on their memory buffer.The Fill Phase: The user looks at the LLM and memorizes a chunk (e.g., var input = new NativeArray<float>). This fills the $7 \pm 2$ slots.The Dump Phase: The user switches to the IDE and types this chunk.The Empty Phase: Once typed, the buffer is empty. The user must switch back to the LLM to get the next chunk.The "Miller Oscillation": This creates a highly specific, rhythmic signature we call the High-Frequency Switch Oscillation (HFSO). A "Bad Focus Loss" session is characterized by frequent, regular switches (e.g., every 10-15 seconds) separated by bursts of text that statistically align with the capacity of working memory (approximately 30-50 characters for code).12In contrast, "Good Focus Loss" (Documentation) exhibits an Arrhythmic Profile. The user might spend 3 minutes reading (long gap), type 5 lines of code (long burst), then spend 10 seconds checking a parameter (short gap), then type 1 word (short burst). The lack of a mechanical rhythm is a hallmark of authentic cognitive engagement.132.3 The "Fluency" of Deception vs. The "Friction" of AuthenticityAuthentic writing is a dynamic process that includes "monitoring, evaluating, and revising".6 It is inherently "friction-full." When a developer writes code based on documentation, they make mistakes. They type a function name, realize it conflicts with another class, and backspace it. They write a loop, realize they forgot to initialize the index, and navigate up to fix it. This results in Low Linearity.Linearity ($L$) is defined as the ratio of the length of the final document to the total number of keystrokes produced:$$L = \frac{|Text_{final}|}{|Keystrokes_{total}|}$$Authentic Composition (Good Focus): $L$ is typically between 0.5 and 0.8. For every 100 characters in the final code, the user might have pressed 120-150 keys (including backspaces, deletions, and navigation).7Transcription (Bad Focus): Transcribers produce a greater number of writing bursts because they are "simply copying language".6 They do not need to revise the logic because the logic (provided by the LLM) is presumed correct. If they make a typo, they fix it immediately (micro-correction), but they rarely delete whole lines or restructure the code (macro-correction). Keystroke Dynamics: The Biometric WitnessTo operationalize the cognitive distinctions outlined above, we must turn to Keystroke Dynamics. This field of behavioral biometrics analyzes the timing information of key press and release events to infer the user's state. While traditionally used for authentication (verifying who is typing), recent research 3 confirms its efficacy in authorship verification (verifying how they are typing).3.1 Fundamental Metrics of Typing BehaviorThe raw data layer for our "Cluely" logic consists of timestamped events: keydown ($t_{down}$) and keyup ($t_{up}$). From these, we derive the primary latencies 16:Hold Time (H): The duration a key is depressed ($H = t_{up} - t_{down}$). This metric correlates with finger motor speed and psychological certainty. Authentic writers often have longer hold times on "decisive" keys (like Enter after a block of logic) compared to transcribers who treat all keys equally.18Flight Time (F) / Down-Down Latency (DD): The time between pressing one key and pressing the next ($DD = t_{down}^{n+1} - t_{down}^n$). This is the most information-rich metric. It represents the "cognitive gap" between characters.Intra-word Flight Time: Time between letters in a word (e.g., 'p' to 'r' in "print").Inter-word Flight Time: Time between the last letter of a word and the first letter of the next (often including the space bar).The Distribution of Flight Times:In authentic typing (including coding with docs), flight times do not follow a normal (Gaussian) distribution. They typically follow a Log-Logistic or Log-Normal distribution with a "heavy tail".13The Head: Fast, automatic transitions (typing familiar variable names).The Tail: Long, cognitive pauses (thinking about logic, reading docs).The Anomaly of Transcription:When a user is transcribing from an LLM (Bad Focus Loss), the "heavy tail" of the distribution is truncated. The "thinking pauses" are removed because the thinking has been outsourced to the AI. The distribution becomes narrower and shifts toward the user's maximum motor speed.6 The "Robotic Rhythm" of transcription manifests as a lower standard deviation in Down-Down latencies compared to the erratic rhythm of composition.3.2 Typing Speed (WPM) as a Contextual IndicatorA common misconception is that "cheaters type faster." While professional typists can reach speeds of 100+ WPM 19, coding speed is rarely limited by finger movement. It is limited by thought.Composition Speed: Research suggests that during complex tasks like programming, the effective generation rate is significantly lower than the user's raw typing speed, often hovering around 15-30 WPM when pauses are included.20Transcription Speed: When copying text (even code), the cognitive bottleneck is removed. Users can approach their "Copy Typing" speed, which is typically 20-40% faster than their "Composition" speed.19Logic for Cluely: We must establish a Baseline Composition Speed for the user during the session (during periods of high linearity and frequent backspacing). If, after a "Focus Loss" event, the user's typing speed suddenly spikes to $1.5\times$ or $2\times$ their baseline, this is a strong indicator of transcription. The user has switched from "Creating" to "Data Entry."3.3 Pauses as Cognitive MarkersPauses are not merely the absence of typing; they are indicators of cognitive effort.9Syntactic Pauses (Good): In authentic coding, pauses occur at syntactic boundaries. A user types if (condition) and then pauses to think about the body of the if statement. Or they type a function signature and pause to plan the variables. These pauses align with the logical structure of the code.Buffer Pauses (Bad): In manual transcription, pauses occur at Visual or Memory boundaries. A user might pause in the middle of a variable name because they reached the end of the line on the source text, or because they reached their 7-chunk memory limit.Feature Extraction: By parsing the code being typed, we can classify pauses. A 2-second pause inside a simple string literal (e.g., print("Hello World")) is suspicious. Why pause there? Likely because the user is reading the next word from the LLM. A 2-second pause after a closing brace } is normal (end of logic block).4. The Phenomenology of "Good" Focus Loss (Documentation)To avoid the "hypocrisy" of flagging legitimate research, the "Cluely" system must positively identify the signature of documentation usage. This section details what "Good Focus Loss" looks like in the data.4.1 The "Foraging" LoopWhen a user switches to documentation, they are entering a "Foraging Loop." This loop is characterized by High Variance in $T_{away}$.Quick Check ($T_{away} < 10s$): The user switches to check a specific parameter name or error code. They find it instantly (CTRL+F) and return.Deep Read ($T_{away} > 60s$): The user is reading a conceptual guide (e.g., understanding Unity's Job System 1). They are scrolling, perhaps highlighting text (mouse events), but not typing.The "Navigation" Signal:Upon returning from documentation, authentic users often engage in Navigation before typing.Scenario: A user reads that BurstCompile requires a static method. They switch back to the IDE. They don't just start typing at the cursor. They might use the Up Arrow key or scroll wheel to move to the top of the class to add the using Unity.Burst; namespace.Biometric Signature: The sequence of events is: Focus Gain $\rightarrow$ Pause $\rightarrow$ Navigation Keys $\rightarrow$ Typing. This "Navigation Sandwich" is a strong indicator of "Good Focus Loss" because it implies the user is integrating the new knowledge into the existing structure, rather than appending a new block.224.2 The "Tentative" OnsetThe "Return-to-Editor Latency" (REL) for documentation users is high. Research into "Interruption Recovery" suggests that resuming a complex task after a break (reading docs) requires a "resumption lag".4The Lag: During this lag, the user is mentally mapping the documentation's variable names (e.g., inputArray in the docs) to their own variable names (e.g., enemyHealthList).The "Translation" Burst: When typing begins, it is often slower than average. The user is performing a real-time translation. They might type inputA, backspace, and type enemyHealth. This "Stutter-Start" is a hallmark of honest cognitive effort.64.3 Low Linearity and "Micro-Edits"Authentic documentation use leads to Low Linearity. The user often misunderstands the docs on the first try.The "Undo" Pattern: A user types a line based on docs, realizes it's wrong (compiler error or logic realization), and deletes it immediately.The "Parameter" Struggle: Users often type a function call, wait for the IDE's intellisense, delete a parameter, and re-type it.Data Point: Authentic essays and code have a significantly higher number of insertions and deletions compared to transcribed text.7 The "Product/Process Ratio" (PPR) for authentic work is often $< 0.8$, whereas transcription approaches $1.0$.5. The Phenomenology of "Bad" Focus Loss (LLM Transcription)"Bad Focus Loss" occurs when the user utilizes an external tool (ChatGPT, Claude) to generate the solution and then transfers it to the IDE. The "Cluely" system must distinguish between Paste-Based transfer and Transcription-Based transfer.5.1 The "Paste" Signature (The Clipboard Heuristic)While the user's query focuses on tab switching, clipboard events are the most direct evidence of "Bad Focus Loss."The "Massive" Paste: Human typing speed is finite. If a paste event inserts 500 characters, and the $T_{away}$ (time away) was only 20 seconds, this is physically impossible to have been typed by the user in the other window (500 chars / 20 sec = 1500 CPM or ~300 WPM, which exceeds world records 19).Formatting Stripping: Code generated by LLMs often contains specific formatting (Markdown code blocks). When users paste this, they might paste the raw text including the backticks (```) or they might paste "perfectly" indented code that doesn't match their current indentation level.Logic: A paste of $>50$ characters with a $T_{away} < 30s$ is highly suspicious. However, a paste of $>50$ characters with $T_{away} > 5$ minutes could be a legitimate copy from a tutorial.5.2 The "Manual Transcription" Signature (The Oscillator)This is the primary adversarial behavior: the user knows copy-pasting is disabled or tracked, so they manually type the LLM's output.The "Miller" Rhythm: As established in Section 2.2, the user is bound by Miller's Law. They cannot memorize 10 lines of code. They must oscillate.Oscillation Frequency: We observe a regular pattern of Focus Loss $\rightarrow$ Focus Gain $\rightarrow$ Type ~30-50 chars $\rightarrow$ Focus Loss.Time Away: The $T_{away}$ in this loop is usually short (5-15 seconds)—just long enough to read and memorize the next chunk.Time Back: The time spent typing ($T_{burst}$) is also short and proportional to the chunk size.The "Robotic" Burst: During the typing phase, the keystrokes exhibit High Rhythmic Consistency. The standard deviation of flight times is low. The user is "in the zone" of motor transcription. There are few "thinking pauses" because the user is not thinking about the code; they are thinking about the letters.3High Linearity: The transcriber rarely backspaces to change the logic. They only backspace to fix typos. This results in a Linearity Index $> 0.95$. The code flows out linearly from start to finish, often ignoring the natural "jumping around" of authentic coding.75.3 The "Second Monitor" Edge CaseA sophisticated user might have ChatGPT on a second monitor and never switch tabs (Focus Loss = 0). While "Focus Loss" logic fails here, Keystroke Dynamics still succeeds.Gaze-Induced Pauses: Even without tab switching, the user must move their eyes to the second screen. This creates a specific "Head-Turn Latency."Pattern: Instead of Tab Switch events, we see periodic Long Pauses in the typing stream.Authentic Pauses: Irregular, aligned with logic difficulty.Gaze Pauses: Regular, aligned with visual chunking (every line or every 5-7 words).Differentiation: If the user types a complex line of code perfectly (high linearity) but pauses for 1 second every 5 words (visual acquisition), this is a strong signature of "Screen-to-Screen Transcription".246. Conclusion: From Surveillance to Authorship VerificationThe solution to the "Hypocrisy of Focus Loss" is not to ban the act of switching tabs, but to analyze the cognitive resonance of the return.We have demonstrated that the behavioral signature of a researcher—characterized by hesitation, non-linearity, and high cognitive load—is fundamentally distinct from the signature of a transcriber—characterized by rhythm, linearity, and high working memory load. By implementing the "Cluely" logic, which specifically monitors Return-to-Editor Latency, Miller's Law Oscillations, and Keystroke Linearity, organizations can allow engineers the freedom to use documentation and the open web while maintaining a robust shield against generative dishonesty.The "Cluely" system does not need to know what is on the other tab. It only needs to know how the user behaves when they come back. If they return like a miner carrying heavy ore (cognitive load), they were researching. If they return like a printer dumping a buffer (motor load), they were transcribing. This nuance transforms the focus loss event from a crime into a clue, resolving the hypocrisy and restoring integrity to the assessment of engineering skill.Citations:.6
